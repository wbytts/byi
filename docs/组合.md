# 组合

本文档只讨论 skill 的组合层级设计，不讨论单个 skill 的基础管理命令。单个 skill 的管理见 [docs/skill-manage-design.md](/Users/wby/codes/github/byi/docs/skill-manage-design.md)。

## 目标

组合层设计要解决这些问题：

- skill 经常会组合使用
- 同一个 skill 可能被多个组合复用
- 不同组合之间可能存在交叉
- 不希望被单一路径树结构绑死

## 结论

组合层建议单独设计，不混入 `byi skill` 第一阶段能力。

推荐保留这些对象：

- `Skill`
- `SkillPack`
- `Domain`
- `Module`

其中：

- `Skill` 是基础能力单元
- `SkillPack` 是可选组合层
- `Domain` 是领域标签
- `Module` 是能力模块标签

## 推荐关系

不建议做成严格树结构：

```text
Domain -> Module -> SkillPack -> Skill
```

因为真实使用里：

- 一个 skill 可以属于多个组合
- 一个组合可以跨多个模块
- 一个组合也可能跨多个领域

更稳的关系是：

- `Skill` 是基础定义
- `SkillPack` 引用多个 `Skill`
- `Domain` 和 `Module` 作为标签存在

也就是：

- `SkillPack` 不拥有 `Skill`
- `SkillPack` 只维护引用关系
- `Domain` 和 `Module` 不作为强父子层级

## SkillPack

`SkillPack` 的作用是：

- 把一组常用 skill 组织成可复用组合
- 面向某个场景、工作流或目标组织 skill
- 允许同一个 skill 被多个组合共享

推荐属性：

- `id`
- `name`
- `description`
- `skill_refs`

其中 `skill_refs` 只保存 skill 引用，不复制 skill 内容。

示意：

```toml
id = "pack:core/release-basic"
name = "release-basic"
description = "Basic release workflow skills"

skills = [
  "skill:core/github-release",
  "skill:core/changelog-helper",
]
```

## Domain

`Domain` 用于表达“属于什么工作领域”。

例如：

- `frontend`
- `backend`
- `ai`
- `devops`
- `content`

建议：

- 作为标签存在
- 可多值
- 允许 skill 和组合同时标记

## Module

`Module` 用于表达“属于什么能力环节”。

例如：

- `scaffold`
- `debug`
- `test`
- `docs`
- `review`
- `publish`
- `deploy`

建议：

- 作为标签存在
- 可多值
- 不与 `SkillPack` 建立强父子关系

## 为什么不建议强树结构

如果做成：

```text
Domain -> Module -> SkillPack -> Skill
```

会遇到这些问题：

- 同一个 skill 放在哪个 pack 下不稳定
- 同一个 pack 跨多个 module 时难以归类
- 同一个 pack 跨多个 domain 时会重复
- 目录结构会被业务关系绑死

所以更推荐：

- 用引用表达组合
- 用标签表达分类
- 用实例表达本地落地

## 与单个 skill 管理的边界

第一阶段建议边界清晰：

- `byi skill` 只负责单个 skill 的纳入、查看、启停、删除和体检
- 组合层以后单独设计和实现

也就是：

- 先把单体 skill 管理做好
- 再叠加组合层

## 后续设计方向

后续如果要做组合层，可以考虑：

1. `byi pack create`
2. `byi pack add-skill`
3. `byi pack remove-skill`
4. `byi pack apply`
5. `byi domain list`
6. `byi module list`

但这些不应阻塞第一阶段的 `byi skill` 落地。
